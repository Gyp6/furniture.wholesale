## 1. Реєстр ресурсів (Endpoints Table)

Цей реєстр визначає основні точки входу в систему для реалізації MVP функціоналу. Всі запити мають префікс версіонування `/api/v1/`.

| Метод | Шлях (Endpoint URL) | Опис (Action) | Параметри | Доступ (Roles) | Успіх (HTTP) | Помилки |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **GET** | `/api/v1/catalog` | Отримання списку меблів | Query: category, limit | Public | 200 OK | 400 |
| **POST** | `/api/v1/auth/login` | Вхід через Better Auth | Body: credentials | Guest | 201 Created | 401 |
| **POST** | `/api/v1/orders` | Створення оптового замовлення | Body: items[], address | User | 201 Created | 400, 409 |
| **PATCH** | `/api/v1/orders/{id}/status`| Зміна статусу замовлення | Path: id, Body: status | Admin | 200 OK | 403, 404 |
| **DELETE** | `/api/v1/catalog/{id}` | Видалення товару з бази | Path: id | Admin | 204 No Content | 404, 409 |

## 2. Специфікація форматів обміну (Data Contracts)

Ми використовуємо підхід розділення DTO для запитів та відповідей, щоб гарантувати безпеку та чистоту даних.

### 📦 Кейс: Створення оптового замовлення
**Request DTO (`CreateOrderDto`):**
```json
{
  "items": [

  ],
  "deliveryAddress": "м. Львів, вул. Залізнична, 12"

```
**Response DTO (`OrderResponseDto`):**
```json
{
  "orderId": "ORD-2026-X77",
  "status": "PENDING",
  "totalPrice": 45000.00,
  "createdAt": "2026-04-11T12:30:00Z"
}
```

## 3. Уніфікована схема помилок (Global Error Schema)

Всі помилки в системі повертаються в єдиному форматі для стабільної роботи Frontend-частини.

**Приклад помилки (409 Conflict):**
```json
{
  "timestamp": "2026-04-11T12:35:00Z",
  "errorCode": "INSUFFICIENT_STOCK",
  "message": "Недостатньо товару 'Стілець Офісний' на складі",
  "path": "/api/v1/orders",
  "details": [
    { "field": "quantity", "error": "Available: 5, Requested: 10" }
  ]
}
```

### Мапа статус-кодів (Status Code Map)

Ми використовуємо стандартні HTTP-коди для класифікації відповідей сервера. Це дозволяє фронтенду (Next.js) передбачувано обробляти результати запитів.

| Код | Назва | Кейс використання у проекті Furniture.Wholesale |
| :--- | :--- | :--- |
| **200** | OK | Успішне завантаження списку меблів, отримання профілю користувача або зміна пароля. |
| **201** | Created | Успішне створення нової картки товару в каталозі або оформлення нового замовлення. |
| **204** | No Content | Успішне видалення товару з каталогу або очищення кошика (відповідь без тіла). |
| **400** | Bad Request | Помилка валідації: передано від'ємну ціну, невалідний UUID або пусте обов'язкове поле. |
| **401** | Unauthorized | Користувач не авторизований (відсутня або недійсна сесія Better Auth). |
| **403** | Forbidden | Клієнт намагається зайти в адмін-панель або змінити ціну товару, не маючи прав адміна. |
| **404** | Not Found | Спроба отримати деталі замовлення або товару за ID, якого не існує в базі PostgreSQL. |
| **409** | Conflict | Порушення бізнес-логіки: спроба замовити 100 стільців, коли на складі залишилося лише 20. |
| **500** | Internal Error | Несподівана помилка сервера: збій підключення до бази даних або помилка в коді NestJS. |

## 4. Інтерактивна документація (Swagger / OpenAPI)

Проєкт використовує підхід **Documentation-as-Code**. Це означає, що технічна специфікація генерується автоматично на основі декораторів у коді NestJS, що гарантує 100% відповідність документації реальному API.

* **Інструментарій:** Бібліотека `@nestjs/swagger` (OpenAPI v3).
* **Локальна адреса:** [http://localhost:4200/docs](http://localhost:4200/docs) (доступно при запущеному сервері).
* **Формат специфікації:** OpenAPI 3.0.0.
