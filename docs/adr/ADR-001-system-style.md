## 1. Контекст (Context)
На початковому етапі розробки системи необхідно визначити макро-архітектурний стиль. Команда має обмежені ресурси (1 розробник) та стислі терміни для реалізації MVP. Основні вимоги до системи:
* **Time-to-market:** Максимально швидкий запуск базового функціоналу.
* **Data Consistency:** Забезпечення цілісності даних (ACID) для фінансових та логічних операцій.
* **Low Infrastructure Overhead:** Мінімізація витрат на хостинг та складність DevOps.

## 2. Рішення (Decision)
Ми обираємо **Модульний Моноліт (Modular Monolith)** як основний архітектурний стиль. 
Бекенд-частина реалізується як єдиний розгортаний юніт (Deployment Unit) на базі фреймворку **NestJS**, але з чітким внутрішнім розділенням на логічні модулі (`Auth`, `User`, `Core`, `Billing`).

## 3. Обґрунтування (Rationale)

### 3.1. Цілісність даних (Data Consistency)
Використання монолітної архітектури дозволяє застосовувати ACID-транзакції на рівні однієї реляційної бази даних (**PostgreSQL 18**). Це критично для забезпечення узгодженості даних без впровадження складних патернів розподілених транзакцій (наприклад, Saga).

### 3.2. Простота розгортання та підтримки
Система пакується в один Docker-контейнер (`standalone` output). Це дозволяє уникнути потреби в налаштуванні Service Discovery, API Gateways та складних мережевих конфігурацій, що притаманні мікросервісам.

### 3.3. Низька затримка (Latency)
Взаємодія між модулями відбувається через виклики функцій у пам'яті процесу, що забезпечує мінімальну затримку порівняно з мережевими викликами (HTTP/gRPC) у розподілених системах.

### 3.4. Перспектива масштабування
Завдяки модульній структурі NestJS, у разі зростання навантаження на окремий функціонал (наприклад, генерація звітів), цей модуль можна буде винести в окремий мікросервіс з мінімальним рефакторингом бізнес-логіки.

## 4. Наслідки (Consequences)

### Позитивні (Pros):
* **Спрощене налагодження (Debugging):** Весь шлях виконання запиту можна простежити в одному лозі.
* **Спрощене тестування:** Можливість проведення наскрізних (E2E) тестів без підняття цілого кластера сервісів.
* **Shared Logic:** Легке перевикористання коду через спільний внутрішній пакет або модуль.

### Негативні (Cons):
* **Tight Coupling (ризик):** При неправильному проектуванні модулі можуть стати занадто залежними один від одного.
* **Single Point of Failure:** Критична помилка в одному модулі може призвести до падіння всього сервера.
* **Deployment Bottleneck:** Будь-яка дрібна зміна в одному модулі вимагає перезбірки та перезапуску всього моноліту.

## 5. Розглянуті альтернативи (Alternatives)

* **Microservices:** Відхилено через надмірну інфраструктурну складність для поточної команди та високий рівень **Overhead** на налаштування міжсервісної взаємодії.
* **Serverless:** Відхилено через потенційну проблему "Vendor Lock-in" та складність локальної розробки/тестування специфічної логіки NestJS.
